# Производительность: где именно просаживается кадр

Отчёт по замерам от 2026-09-20. Машина: Apple M5 Pro, Chrome headless **на реальном GPU** (ANGLE Metal),
production-сборка клиента. Инструменты и сырые данные — в конце документа.

## Короткий ответ

Частота кадров как таковая не проседает. Во **всех** проверенных ситуациях — от начала матча до боя
2400 юнитов на карте 160×160, включая ретина-разрешение и вчетверо замедленный процессор — игра держит
ровные 60 fps, а главный поток занят на 12–31 % кадра.

Просадки, которые заметны в игре, — это **одиночные длинные кадры на 30–400 мс**, а не падение fps. Их
источники найдены, их немного, и все они одноразовые (случаются один раз за матч или на действие):

| # | что | сколько | когда |
|---|---|---|---|
| 1 | создание `AudioContext` при первом звуке | **80–95 мс** | один раз за матч, обычно в первом бою или на первом клике по карте |
| 2 | компиляция шейдеров на первом кадре матча | **56 мс** (17 программ) | один раз, на старте матча |
| 3 | конструктор `GameView` + первый коммит React | **104 мс** | один раз, на старте матча |
| 4 | переключение галочки «тени» в настройках | **35–374 мс** | каждый раз, когда её трогают |
| 5 | пересборка террейна после пожара | 1.5 мс на карте 64×64 | каждый раз, когда лес догорает |

Пункт 1 — самый вероятный кандидат на то, что ты заметил: он бьёт **в середине игры**, а не на загрузке,
и воспроизводится в каждом запуске.

## 1. Как измерялось

Инструменты лежат в `scripts/perf/`:

| файл | что делает |
|---|---|
| `probe.js` | профилировщик кадров; внедряется в страницу **до** её собственных скриптов |
| `run.mjs` | прогоняет клиент по набору сценариев, пишет сырые данные в `data/perf/*.json` |
| `report.mjs` | сводка и разбор просадок по этим данным |
| `trace.mjs` | трейс Chrome — для того, что не видно изнутри страницы (GC, компиляция шейдеров, GPU-процесс) |
| `alloc.mjs` | сэмплирующий профиль аллокаций: кто кормит сборщик мусора |
| `experiment.mjs` | A/B: меняем одну вещь в рантайме и меряем то же самое ещё раз |

Профилировщик пишет на **каждый кадр**: длину кадра, `busy` (сумма измеренных фаз), `gap` (время между
концом работы кадра и началом следующего — туда попадают коммит React, GC, композитинг и просто ожидание
vsync), фазы `sim / input / sync / render / hud / react / mini`, подфазы шага симуляции
(`cmds / grid / move / fires / build / deaths / gates / pop / fog`, плюс `field / expand / query / bot`),
трафик WebGL (МБ в буферы, число загрузок, число слинкованных программ), размер кучи, число
юнитов / сущностей / draw call'ов / треугольников и события симуляции — чтобы просадку можно было назвать,
а не угадать.

Чтобы измерить React, профилировщик перехватывает `MessageChannel` до загрузки React: его коммиты идут
отдельной задачей между кадрами, иначе они выглядят как «простой».

### Чего эти числа не говорят

* `requestAnimationFrame` залочен на 60 Гц, поэтому p50 = 16.7 мс везде. Запас виден не в fps, а в `busy`.
* Headless: нет оконного композитинга ОС, нет соседних вкладок, машина в остальном простаивает.
* В сценариях `stress*` юниты бессмертны (так устроен `?stress=`) — бой не кончается, нагрузка не спадает.
* В скирмише игрок ничего не делает, армию строит только бот; поэтому «середина матча с большой армией»
  моделируется стресс-картами.
* Мультиплеер (`NetSession`) не измерялся — нужен сервер и второй клиент.
* Напоминание про масштаб: `MAX_POP = 60`, солдат стоит 2 популяции. В реальном матче 1×1 на карте живёт
  **~100–120 юнитов**, в FFA на шестерых — до ~350. Сценарии на 600/1200/2400 юнитов — это 2×/4×/8× от того,
  что игра вообще способна собрать.

## 3. Причины просадок

### 3.1 Первый звук в матче: `new AudioContext()` — 80–95 мс

**Что видно.** В каждом запуске ровно один кадр длиной 83–97 мс, и всё это время сидит внутри `sim`
(то есть внутри `session.update` → `sim.step`), при том что ни одна из подфаз шага — поиск пути, бот, сетка,
туман, смерти — ничего не показывает. Повторилось в шести независимых запусках: `mid-3x` (86 мс),
`forest-fire` (95 мс), `stress600-battle` (87 мс), `stress600-noshadow` (85 мс), `stress1200-battle` (90 мс),
`retina-battle` (83 мс).

**Доказательство.** Трейс Chrome в том же кадре:

```
87.6 ms  Renderer  RunTask
86.9 ms  Renderer  FireAnimationFrame  →  FunctionCall  →  v8.callFunction
82.2 ms  Renderer  AudioOutputDevice::GetOutputDeviceInfo      ← синхронный IPC в аудио-сервис
```

**Механика.** `AudioFx.ensure()` ([audio.ts:14](../packages/client/src/game/audio.ts#L14)) создаёт
`AudioContext` лениво. Первое создание синхронно опрашивает аудиоустройство и блокирует главный поток.
Вызывается это либо из `pointerDown` ([input.ts:290](../packages/client/src/game/input.ts#L290) →
`audio.unlock()`), то есть на первом клике игрока по карте, либо — если игрок ещё не кликал — из первого
звукового события симуляции, то есть **прямо посреди боя**, внутри шага симуляции.

**Изолированный замер** (`node scripts/perf/experiment.mjs audio`), вне игрового кадра:

```
первый  new AudioContext()  →  71.1 мс блокировки главного потока
второй  new AudioContext()  →   0.1 мс
```

**Фикс.** Создавать контекст на клике по кнопке «ИИ»/«Старт» в меню: жест пользователя там уже есть, а 85 мс
на экране загрузки никто не заметит.

### 3.2 Компиляция шейдеров

**Что видно.** На первом кадре матча линкуются **17 программ**, кадр длится **56 мс**. Дальше в матче новых
компиляций нет — все материалы сцены создаются в конструкторе рендерера и рисуются на первом же кадре
(`frustumCulled = false`, пустые наборы тоже проходят через `setProgram`).

**Но:** переключение настройки «тени» меняет дефайны всех материалов, и следующий `gl.render` пересобирает
программы:

```
stress600-noshadow, прогон 1:  кадр 376.6 мс, из них render 374.1 мс, слинковано 5 программ
retina-noshadow,    прогон 2:  кадр  34.9 мс, из них render  32.4 мс, слинковано 5 программ
```

Разброс между запусками большой (одни и те же 5 программ — от 35 до 374 мс), но в обоих случаях это
единственный длинный кадр в сценарии, и он целиком лежит внутри `gl.render`. Скорее всего дело не только в
самих программах, но и в пересоздании конвейеров Metal для всех 139 мешей сцены.

**Фикс.**
* прогреть шейдеры до первого кадра: `gl.compile(scene, camera)` в конце конструктора `Renderer`, пока на
  экране ещё лоадер;
* не трогать `gl.shadowMap.enabled` в [`setShadows`](../packages/client/src/game/renderer.ts#L1347) — гасить
  тени через `sun.shadow.intensity = 0`, чтобы дефайны материалов не менялись и программы не пересобирались.

### 3.3 Старт матча: 104 мс в конструкторе вьюхи и первом рендере React

**Что видно.** В сценарии `boot` один кадр на 104.5 мс, из которых **103.9 мс — `react`**. Внутри этого
коммита: конструктор `GameView`, конструктор `Renderer` (139 `InstancedMesh`, террейн, теневая карта),
`warmUnitArt` (второй WebGL-контекст, рендер портретов юнитов и `toDataURL` на каждый) и первая отрисовка
всего HUD. Следующий кадр — те самые 56 мс на шейдеры.

Итого переход «меню → игра» стоит **~160 мс заблокированного потока** плюс загрузка моделей (в `boot` видно
паузы в 2.3–3.9 с — это `Models.load()`, один раз за сессию).

**Фикс.** Это происходит под лоадером, так что терпимо. Если захочется сгладить — рендерить портреты
порциями (через `requestIdleCallback`) и прогревать шейдеры там же.

### 3.4 Длинные кадры вне JS — 74–105 мс

В одном прогоне (`mid-selected`, старая серия) три кадра по 105/79/74 мс, у которых **вся** длительность
лежит в `gap`: JS-фазы пусты, программы не линковались, GC не срабатывал. Такие кадры совпадали с началом
боя (растущее число частиц, первые смерти, первые декали). Правдоподобное объяснение — создание Metal-овских
pipeline state объектов в GPU-процессе при первой отрисовке набора инстансов, которого до этого не было на
экране; главный поток при этом ждёт на swap. Подтвердить это изнутри страницы нечем, а в трейсе GPU-процесса
таких событий поймать не удалось — поэтому оставляю как наблюдение, а не как установленную причину.

Практический вывод тот же, что и в 3.2: прогрев (`gl.compile` + по одному инстансу в каждый набор на первом
кадре) закрывает и этот случай, если он действительно в этом.

### 3.5 Пожар: пересборка цвета террейна и декора

68 сгоревших клеток на карте 64×64 → `refreshTerrainColors` + `rebuildDecor` одним кадром на **1.5 мс**.
Не просадка, но масштабируется с площадью карты: на 160×160 это уже ~9 мс, то есть пропущенный кадр.

## 4. Постоянные расходы: где лежит запас

### 4.1 Инстанс-буферы заливаются целиком каждый кадр — и половина фазы `render` уходит на это

`InstanceSet.end()` ([renderer.ts:195](../packages/client/src/game/renderer.ts#L195)) ставит
`needsUpdate = true` на `instanceMatrix`, `instanceColor` и `aAnim`. Без `updateRanges` three.js заливает
**весь буфер**, независимо от `mesh.count`: `WebGLAttributes.updateBuffer` делает
`gl.bufferSubData(target, 0, array)` целиком, а вызывается это из `projectObject` для каждого **видимого**
объекта — даже с нулём инстансов.

В сцене **139 `InstancedMesh`**: 84 набора зданий (2 века × 7 типов × 3 стадии × обычные + призраки),
половинки заборов, ворота, 14 наборов юнитов, рудники, декор, кольца, полоски здоровья, стрелы, пунктир
маршрутов. Большинство почти всегда пустые. Измерено: **396 загрузок и 4.9 МБ на кадр** при 1300 юнитах
(и ровно столько же загрузок — 395 — в скирмише, где на карте 20 юнитов).

A/B прямо в рантайме (`node scripts/perf/experiment.mjs …`), одна и та же сцена до и после:

| вариант | загрузок/кадр | МБ/кадр | `render` | `busy` |
|---|---|---|---|---|
| как сейчас | 396 | 4.86 | 1.27 мс | 3.08 мс |
| `visible = count > 0` (прятать пустые наборы) | **52** | **1.19** | **0.68 мс** | **2.87 мс** |
| `addUpdateRange` (грузить только занятую часть) | 415 | **0.23** | 1.60 мс | 3.29 мс |

Вывод: **прятать пустые наборы — чистый выигрыш, фаза `render` падает вдвое.** А вот `updateRanges`
сокращает трафик в 21 раз, но на этой машине обходится дороже, чем экономит (three.js на каждый буфер
сортирует и сливает диапазоны, а Apple с её общей памятью на целом `bufferSubData` не спотыкается). Имеет
смысл только там, где узкое место — шина: телефоны, интегрированная графика.

**Дополнение (матч на 100 игроков).** Ёмкость наборов считается от числа игроков, и при сотне набор юнитов —
десятки тысяч экземпляров: целиком это 19,8 МБ за кадр при любом числе юнитов в наборе. Поэтому наборы от 2048
экземпляров теперь заливают только занятую часть (`RANGED_UPLOAD_CAP`), маленькие — по-прежнему целиком. На
повторе 100 ботов (8-я минута, 2000 юнитов) заливка упала до 0,6 МБ/кадр, а после отсечения по камере — до
0,2 МБ. Там же нашлась главная статья `sync`: `playerColor` искал цвет линейно через `getHex()` (перевод из
линейного пространства в sRGB на каждое сравнение) — 45 % процессора кадра; теперь это словарь, `sync`
10,5 → 0,8 мс. Подробнее — DESIGN.md, «Отрисовка большого матча».

Фикс — одна строка:

```ts
  end() {
    this.mesh.count = this.count;
    // пустой набор не должен стоить ничего: three.js пропускает невидимый объект до того, как зальёт буферы
    this.mesh.visible = this.count > 0;
    this.mesh.instanceMatrix.needsUpdate = true;
    this.mesh.instanceColor!.needsUpdate = true;
    this.anim.needsUpdate = true;
  }
```

### 4.2 Наведение мышью перебирает весь мир каждый кадр

`pickEntity` ([input.ts:153](../packages/client/src/game/input.ts#L153)) проходит по всем сущностям и
проецирует каждую в экранные координаты — на каждом кадре, пока курсор над картой. Измерено (это видно
только в сценариях с курсором, `*-hover`):

| сущностей | `input` на кадр |
|---|---|
| 21 (начало скирмиша) | 0.08 мс |
| 586 (600 юнитов) | 0.28 мс (макс 1.2) |
| 920 (1200 юнитов) | 0.30 мс (макс 3.6) |
| 610, процессор ×4 медленнее | 0.51 мс (макс 2.1) |

Линейно по числу сущностей, ~0.43 мкс на штуку. Сейчас это не проблема, но это единственное место в кадре,
которое растёт линейно и ни на что не опирается.

**Фикс.** Пересчитывать только когда курсор сдвинулся, и брать кандидатов из `sim.grid` вокруг точки под
курсором вместо полного перебора.

### 4.3 Мусор в кадре

Честная оговорка: измерить скорость аллокаций точно не вышло — профилировщик кадров сам читает
`performance.memory` каждый кадр и оказывается первым в собственном профиле. Что видно надёжно, так это
**стоимость сборки**, а она из трейса: ~0.2 % главного потока (см. раздел 5).

По коду мусор на кадр всё же есть, и на слабой машине он будет стоить дороже:
`known.set(id, {...})` в `sync` — новый объект на каждое видимое здание каждый кадр
([renderer.ts:1032](../packages/client/src/game/renderer.ts#L1032)); два `new Set` на кадр
([renderer.ts:957](../packages/client/src/game/renderer.ts#L957)); `THREE.Vector3` на каждую точку маршрута
в `tracePath`; `new THREE.Color` на каждый вызов `Particles.emit` (это единственное, что видно даже в
испорченном профиле — 20 % выборки).

## 5. Что проверено и оказалось не проблемой

* **Сборка мусора.** Из трейса за 15 с боя на 600 юнитов: 48 молодых сборок, самая долгая 0.77 мс;
  2 полных, самая долгая 2.0 мс. Итого ~0.2 % главного потока, и ни одна просадка с GC не совпала.
* **Поиск пути.** Приказ «атаковать» всей армией из 600 юнитов раз в секунду в течение 20 с — ни одного
  кадра длиннее 17.7 мс. Бюджеты `budgetPerTick` / `workPerTick` работают: `field` в среднем 0.05 мс на кадр.
* **HUD и React.** Пересборка состояния HUD и перерисовка идут 10 раз в секунду и стоят суммарно
  0.06–0.08 мс на кадр (A/B с полностью отключённым HUD). Выделение 104 и 204 юнитов ничего не меняет.
* **Мини-карта.** 0.02–0.05 мс на кадр даже на карте 160×160.
* **Draw call'ы.** 18–47 на кадр, до 600 тыс. треугольников — инстансинг работает как задумано.
* **Скорость матча 5×.** Симуляция 1.6 мс на кадр при 600 юнитах, просадок нет.
* **Строительство заборов.** Стройплощадки не трогают проходимость, копия навигации во вьюхе (`vcopy`)
  стоит 0.2 мс. Ни одного длинного кадра.
* **Ретина.** 2268×1473 против 1600×900: разницы в кадре нет (`render` 1.52 против 1.65 мс) — GPU не является
  узким местом на этой машине.
* **Вчетверо замедленный процессор.** 600 юнитов: `busy` ≈ 4.8 мс (p50) и 9.8 мс (p95) из 16.7. Всё ещё
  ровные 60 fps.

Единственный кадр за все 32 сценария (~32 000 кадров), который просел из-за **настоящей работы симуляции**:
`cpu4-1200`, кадр 26 мс — `move 16.4` из которых `field 8.4` / `expand 8.3`. То есть 1200 юнитов *и*
вчетверо замедленный процессор — это та точка, где один тик перестаёт помещаться в кадр. В реальном матче
(до ~350 юнитов на шестерых) до этого не доходит.

## 6. Что делать, по приоритету

1. **Создавать `AudioContext` заранее** — одна строка, убирает единственную просадку, которая случается
   в бою (~85 мс в каждом матче).
2. **Не пересобирать шейдеры при переключении теней** — убирает фриз на 35–374 мс.
3. **Прогреть шейдеры до первого кадра** (`gl.compile`) — переносит 56 мс со старта матча под лоадер и,
   возможно, закрывает наблюдение 3.4.
4. **Прятать пустые наборы инстансов** (`mesh.visible = count > 0`) — одна строка, фаза `render` падает
   вдвое (1.27 → 0.68 мс), загрузок в буферы 396 → 52. Проверено экспериментом.
   `addUpdateRange` в придачу — только если целиться в телефоны: трафик падает в 21 раз, но CPU на этой
   машине дороже.
5. **Не перебирать мир на наведение каждый кадр** — снимает единственную линейную по числу сущностей
   статью расходов в кадре.
6. **Мультиплеер: ограничить догон по времени, а не по числу тиков.**
   [session.ts:204](../packages/client/src/game/session.ts#L204) при отставании больше 40 тиков прокручивает
   до 200 тиков за один кадр. При измеренных 1–2 мс на тик (600 юнитов) это фриз до 200–400 мс после любого
   сетевого затыка. Не измерялось — вывод из кода и из стоимости тика.
7. Мусор в кадре — когда дойдут руки.
